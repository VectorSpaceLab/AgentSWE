# Task goal: previewable, provenance-bound Acceptance mode

Edit the supplied Dyad repository to complete the existing **Acceptance**
agent mode as an auditable, bounded develop/chat workflow inside a real
app. Keep the stable requirements, behavior-centered mutation testing,
focused fix before regression, honest unresolved outcomes, durable run reads,
and retryable `resume`/`cancel` control transactions from the supplied task
contract.

Add two independent production capabilities.

First, let users run the Playwright target generated by an Acceptance
session from Dyad's preview surface and observe durable setup, running, and
terminal progress. The main process owns the session. A start is retryable
after a lost response, Stop uses the existing Tests cancel path, a renderer
remount does not lose the session, and a process restart turns abandoned
work into an honest terminal outcome instead of claiming success or silently
re-running it.

Second, create a durable test attestation only from a completed preview
session. Bind it to the acceptance run and generation, the exact target
fingerprint, and the deterministic app workspace revisions observed before
and after execution. A passing runner result does not mean passing
acceptance evidence when code or tests changed in flight, the result is
incomplete, the session is stale or foreign, or the revisions cannot be
verified.

The surfaces must interact: only a current, revision-matching `passed`
attestation can support a requirement or a terminal `passed` run.
Reordered, duplicate, delayed, cancelled, infrastructure-limited,
stale-generation, and invalid preview output remain bounded diagnostic
evidence and cannot overwrite a newer generation, consume the repair budget
twice, or resurrect an earlier approval.

The mode remains the stored and active chat mode `acceptance`. Use Dyad's
production `chat:stream`, the local agent/app boundary, the test runner, the
contract-defined IPC, main-owned persistence, the Preview/Tests
presentation, SQLite, and the Git workspace. Deterministic integration tests
may use the existing fake engine, fake app runner, SQLite, and hybrid
harness; a packaged Electron GUI or a live model is not required.

Non-goals are a general CI service, a second agent runtime, a live
third-party test oracle, automatic continuation of work after restart, a
general browser replacement, or treating admission/stream completion as a
test or acceptance-fix pass.

In addition, the acceptance surface must be independently verifiable: the
product publishes the current acceptance target so that the caller need not
guess it; the target fingerprint is the real digest of the target bytes at
the moment of admission; the workspace revision changes with the content and
reverts when the content is restored; denied requests enter an append-only,
bounded ledger that does not echo foreign identifiers; the same operation
identity carrying different content is refused as a conflict; there is at
most one attestation per session, and late callbacks, duplicate stops, and
restart reconciliation all return that same attestation; a restart
reconciles interrupted work into an honest terminal state with a reason,
while ordinary chat modes change no acceptance bytes.
